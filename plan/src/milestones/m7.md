      The revisions are served as JSON and through server functions. The rule is X3's, run in

      - the snapshot, through git's CLI: a copy of the index, `git add -A` and `git write-tree`
      - the carry: a three-way merge of trees, from where the start left the base branch, which
        gix writes as `git merge-tree` does
      - the diff, merge-base and ancestry, through gix

      C30's record holds the start, its tree, the fork and the base branch, and the worktree
      finds its node with `reef_api::work::on_worktree`. Each capture adds the SHAs it read
      through `POST …/work/{id}/captures`, naming its start by the pinned commit, and reads
      through reef's `git` module, where gix is already pinned.

      A carry that conflicts names its files on the revision. Whether a seal leaves out untracked
      files the node never committed is this node's to decide: X3's live runs captured Python's
      `__pycache__`.

# M7 Code tied to its node

Each node keeps the diff that did its work. Commits are squashed regularly, so reef reads git
only to capture a node's changes, and stores them itself. The user comments on the changed lines.

reef's CLI extracts the changes from the node's local checkout, and nothing is pushed or
fetched. git's hooks keep a draft current while the node is worked on, and Claude Code's Stop
hook seals it once the node is done.

[X3](../design/code-and-comments.md#what-x3-found) found how to pick out one node's changes. Its
diff runs from where it started, carried over whatever its base branch brought in since. Nodes
worked on at once each get a worktree, and nodes in a row share a branch.
