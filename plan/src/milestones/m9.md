    why: Nobody knows whether `claude -p` with stream-json, driven from Rust, or an Agent SDK sidecar can pause on AskUserQuestion and ExitPlanMode for an answer from elsewhere.
    what: The plan knows which driver reef uses, and how a question and a plan reach the app and come back.
    details: |
      `claude -p` over stream-json, driven from Rust, does it alone. With
      `--permission-prompt-tool stdio`, every prompt the session would show a user, questions and
      plans included, comes to the host as a `can_use_tool` control request and waits for its
      control response. The Agent SDKs drive this same protocol over the same CLI, so a sidecar
      would add a runtime and change nothing.

      Tried in `spikes/x5-headless`, a stub host in Rust driving Claude Code 2.1.330 with Sonnet
      5.5 at low effort, in X4's scratch repo with its stub MCP server and hooks. In two runs it
      answered each question with its first option, rejected each first plan with feedback and
      approved the revision. Claude revised the plan from the feedback both times. One question
      was held 200 s and the session carried on from the answer. The repo's `.mcp.json` server
      and every hook ran, Stop before the turn's `result`, a second message carried the session
      on, and closing stdin ended it. Each node cost $0.15 to $0.17.

      The server never runs Claude, since a server that spawned sessions would run code for anyone
      who reached it. So `reef loop run`, started by the user on their own machine, attaches to
      central reef and spawns a fresh `claude -p` a node, in a `reef:<id>` pane its sessions find
      through `REEF_PANE`. Central reef keeps its transcript and pending prompts in memory,
      publishes `session-changed`, and queues the app's starts, answers and replies as orders the
      runner long-polls for.

    why: The terminal loop needs the user at the terminal, and reef can't show a session anywhere else.
    what: A runner the user starts on their own machine, `reef loop run`, attaches to central reef. A loop the app starts on it runs Claude headless there, a fresh session a node, its transcript streamed into a reef-app panel.
    details: |
      `reef loop run` (`crates/reef/src/run`) attaches the checkout to central reef as a session
      of its own, on a `reef:<id>` pane it names to each Claude session in `REEF_PANE`. Each node
      gets a fresh `claude -p` over stream-json with `--permission-prompt-tool stdio`, its
      `CLAUDE*`, `ZELLIJ*` and `TMUX*` variables scrubbed, so its MCP server and hooks find the
      runner's loop. `run::decide` follows the loop: a session when the app starts or wakes it,
      a fresh one once Stop has acted on the node's end, an end at a pause or with nothing taken,
      and a wait for the user's reply mid-node. The Stop hook tells a runner's session that the
      runner starts the next node, and a loop on a runner's pane is refused wider than one.

      Central reef runs nothing. `service/sessions.rs` keeps each runner's transcript, its last
      2,000 entries, and the prompts it waits on, in memory, publishes `session-changed`, and
      queues the app's answers and replies as orders the runner long-polls for by number. The
      app's start, pause and stop change the runner's loop and wake it. A runner its service
      forgot attaches again with the transcript it holds, and one unheard from for a minute
      reads as gone.

      reef-app's sessions panel opens from the bar, which counts live sessions and waiting
      prompts. It lists each runner with its loop's buttons, and a terminal's loops beside. The
      picked runner's transcript follows the project's stream, each prompt is a card to allow or
      deny, and a reply box shows while Claude waits mid-node.

      Tried live with Claude Code 2.1.330 and Sonnet 5.5 at low effort, through the dx-built app
      on scratch data, driven by Playwright. Started from the panel, L1 was taken, its Bash
      prompts were allowed from cards, and it was done and committed for $0.12. L2 then ran in a
      fresh session, its plan approved from a card. The transcript grew from 0 to 65 entries
      with no reload. The run found that reef's tools need `plan` in a multi-plan project even
      when the loop narrows to one, now C74.

      Known limits: a runner works one node at a time; the service forgets transcripts when it
      restarts, keeping only what a runner sends again; re-attaching after a restart is covered
      by the 404 its client reads, not by a live restart.

      `sessions.rs::an_answer_picked_in_the_app_reaches_the_session` runs a runner whose stub
      Claude asks at each node: the question reaches the service with its header and choices,
      the answer sent as the app sends it reaches the stub, which says so, and its node is done
      before the next node's question. `check.py`'s `c46` picks a choice in the browser, then
      answers the next node in the user's own words.

      Tried live with C47, with Claude Code 2.1.330 and Sonnet 5.5 at low effort through the app:
      on three nodes Claude asked which greeting, colour or welcome, each card's first choice was
      picked, and Claude carried on from it, *red, the colour you picked*, each node done and

    details: |
      `decisions::read` reads a session's transcript, which Claude Code writes the same way in a
      terminal and under a runner: each ExitPlanMode and AskUserQuestion call and its result, the
      node from the backticked name on each next_task result's first line, a terminal's feedback
      from after *the user said:*, and answers from the result's own record. reef's Stop and a new
      SessionEnd hook keep them through `POST .../nodes/{id}/decisions`, each by its tool call's id,
      so a transcript read again keeps nothing twice and an answer read later fills its question
      in. Stop places one asked before any next_task on the node the session is on; SessionEnd
      places only what its transcript names. `reef claude install` adds SessionEnd, and this
      repo's settings were written again by it.

      Central reef keeps them in a new shoal table, `DecisionRow`, a row a decision partitioned by
      node, every older table's fingerprint unchanged, so no fresh data directory is needed: the
      scratch serve opened a data directory the previous binary wrote and read it back.

      Found live and fixed: approving a plan with *clear context* ends the planning session's
      ExitPlanMode as `User rejected tool use`, and SessionEnd ran before those last lines were
      written. The clear's new session begins with the plan as `planContent` and a
      `data-flow-records` line naming the planning call, so its Stop now keeps that call
      approved, and an approval stands against any later read.

      Tried live with Claude Code 2.1.330 and Sonnet 5.5 at low effort: two terminal sessions in a
      private tmux pane, each answering its question, rejecting its first plan with feedback and
      approving the revision with a clear, and C47's runner session read again by its SessionEnd.
      The terminal node kept its question, its rejected plan with the feedback as typed and its
      approved revision, answered in the terminal; the runner's node the same three, answered in
      the app. They read back after the server restarted.

      Known limits: a clear's approval is placed by the new session's Stop, on the node its pane's
      loop or checkout is on, so one approved in a session whose implementing turn never ends is
      left as the planning session read it.
