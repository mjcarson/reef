  status: done

    why: Nothing records which session feeds a project, which node it holds, or whether its loop is paused.
    what: '`reef loop start|pause|stop|ls` keeps one loop per pane, with its project, an optional plan, its session, its current node and the node whose end it acted on, and `reef hook session-start` hands it to each session that starts in its pane.'
    details: |
      A loop can't be keyed on the session id: X4 found that every `/clear`, including a plan
      approval's, starts a new session. SessionStart(clear) hands the loop to the new one.

      Built in `crates/reef-api/src/loops.rs`, `central/reef-service/src/store/loops.rs` and
      `service/loops.rs`, and `crates/reef/src/loops.rs`. A loop is kept by its `Pane`: zellij's
      session and pane, else tmux's socket and pane, else `CLAUDE_PID`, the Claude Code process,
      which a clear keeps. A headless Claude Code 2.1.327 run showed its Bash commands and its
      SessionStart and Stop hooks all get `CLAUDE_PID` and `CLAUDE_CODE_SESSION_ID`, the
      session's current id. So `! reef loop start` finds its pane and session in the session's
      own pane, or `--pane` names one, as `reef loop ls` prints its key.

      Every loop is a `LoopRow` of one constant partition, keyed by its pane, so a pane keeps one
      loop, and every change (`POST /api/v1/loops`) reads them all under one lock. A start where
      a loop of the same project and plan is runs it again, and one of another is `busy`.
      `LoopEdit::Hold` takes a node, one at a time, refused as `held` while another loop holds
      it, for next_task (C40). `LoopEdit::Acted` records the node whose end the Stop hook acted
      on (C41). `reef hook session-start` reads the hook's `session_id` and hands it the pane's
      loop, printing nothing, since a SessionStart hook's output is added to the context.

      Tried live in a headless session against a scratch `reef-serve`: the loop Claude's Bash
      started was found by its Stop hook in the same pane, and handed over. The new table moved
      the schema's pin, but the binary read back a data directory C37's wrote.

      Known limits: a loop whose pane closed stays until `reef loop stop --pane` ends it, holding
      its node meanwhile. Nothing installs the hook until C42.

    details: |
      Built in `crates/reef/src/task.rs`, served as the tool in `crates/reef/src/mcp.rs` and as

      keyed as `claude:<pid>` was the one next_task took `A` for, passing over a queued `B` that

  description:
    why: Without it the user types *next* after every node.
    what: '`reef hook stop` lets Claude stop and says nothing while it waits on the user. Once the node the pane''s loop holds is done, it acts once on that node''s end, whatever `stop_hook_active` says: it names the next node and `/clear`, or says the loop is paused or nothing else is ready.'
    details: |
      X4 found `stop_hook_active` stays true across a chain of blocks, tool calls and plan
      approvals, so it can't be the guard. C39's loop keeps the guard instead, `acted`, which
      `LoopEdit::Acted` records, and whether the loop is paused. A block shows in the terminal as

      Built in `crates/reef/src/task.rs`, beside next_task's `choose`. `end_of` is the node whose
      end a turn's end is: the loop's, once it is done and its end not acted on. `after` is what
      comes next, as `choose` would take it for a node done: `Paused`, `Finished`, or `Next`, the
      first ready node no other loop holds. `ended` reads the pane's loop and records
      `LoopEdit::Acted` before it says anything, and the store answers a second record of the same
      node `ActedAlready` under the loops' lock, writing nothing (409), so two Stops never both act.
      `reef hook stop [--pane KEY]` seals first, as C56 does, then ends the loop's node, its pane
      the key named or else the session's from its environment. Claude Code shows the user a Stop's
      output only when all of it is JSON, so when the loop has something to say, the seal's lines
      and its line go out as one `systemMessage`. Otherwise it prints the seal's lines as before.
      The skill's step 5 now says the Stop hook names the next node.

      Known limits: until C61 types it, the user types `/clear` and asks for the next node. A node
      marked done in a turn that ends before its commit is acted on all the same. A paused loop's
      end is acted on, so once it runs again the user starts the next node. Nothing installs the
      hook until C42.

  title: C61 Clearing between nodes
  status: done
  needs:
  - C41
  docs:
  - ../design/feed-loop.md#the-terminal-loop
  description:
    why: No hook output, tool or command clears an interactive session, so each node would carry the last one's context.
    what: Once a node is done and another is next, `reef hook stop` starts `reef hook clear`, which types `/clear` and a kickoff into the session's zellij or tmux pane once it is idle with an empty input box. Elsewhere the user types `/clear` and `next`.
    details: |
      Built in `crates/reef/src/clear.rs`. For `Ending::Next` in a zellij or tmux pane, with the
      session id and `CLAUDE_PID` known, `hook::stop` spawns `reef hook clear` in its own process
      group, its output appended to `$XDG_STATE_HOME/reef/clear.log`. The injector polls the
      pane's loop, `claude agents --json` for the pid's session, and the pane's screen. It types
      only while the loop still holds the node whose end it acted on, the process still runs the
      session it watches, the session is idle and the box is empty. Then it types `/clear`, waits
      for the pid's new session, and types the kickoff the same way. Enter is pressed only on a
      box that reads back as what was typed. It steps aside once a turn starts that it didn't type,
      or after ten minutes.

      The box is read with its ANSI codes (zellij `dump-screen --ansi`, tmux `capture-pane -e`),
      since Claude Code draws its placeholder and suggested prompt faint, and a named session's
      top rule holds its name. SessionStart(clear) now names the next node as `additionalContext`
      when the loop is between nodes, so `next`, or the typed kickoff, starts it. A plan
      approval's clear, mid-node, is told nothing.

      Tried live with Claude Code 2.1.330 and Sonnet 5.5 on a scratch reef-serve, in zellij, plain
      tmux and neither, each on a private tmux server with a scrubbed environment. In zellij and
      tmux, the next node's next_task ran with nothing typed, and its session's first turn was at
      44.4k, a fresh session's. A draft typed during a node held the injector, untouched, until it
      was erased, and sending it made the injector step aside. Without a multiplexer, `/clear`
      and `next` started the next node. The first run found the named session's labelled rule,
      which the fixtures now cover.

# M8 Claude fed from the terminal

The loop in the user's own Claude Code session. next_task hands Claude the next node by the
user's queue. Claude plans it in plan mode, the user answers its questions and approves the plan,
and Claude implements it and marks it done. Claude then resolves any open comments, and the Stop
hook clears the context and starts the next node. [X4](../design/feed-loop.md#the-terminal-loop) proves the pieces
first.
