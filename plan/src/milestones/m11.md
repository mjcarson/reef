- id: C92
  title: C92 A plan follows a branch
  status: done
  optional: true
  needs:
  - C49
  docs:
  - ../design/store.md#plans-branches
  description:
    why: A project follows one branch, so every plan's doc links are checked at that one commit, and a plan for another branch can't link that branch's docs.
    what: A plan names the branch it follows, its docs are read and checked there, a remote project's clone fetches every branch a plan names, and `reef plan ls` shows each plan's branch.
    details: |
      The branch is kept in a new `PlanBranchRow` table (partition project, sort plan, a JSON
      record), so `PlanRow` didn't change and no fresh data directory is needed: every other
      table's fingerprint stayed where it was pinned. `reef plan branch <name> <B>` (or `--clear`)
      and `reef plan new <name> --branch B` set it through `PUT …/plans/{plan}/branch`, a new path,
      which an older server answers with no route rather than dropping the branch. The answer is
      `Branched`: `applied` with the plan's `PlanInfo`, `no-branch` (422) for a branch the repo
      hasn't, or `refused` (422) with the problems the plan's docs at the new branch would add,
      judged under the plan's write lock against its docs at the old branch. Each change is kept in
      the plan's history as `Edited::Branched`, and told as `plan-branched`.

      Docs are read per plan: `Docs::of(project, branch)`. A remote project's plan reads its
      branch's commit from `KeptRemote.branches`, a serde-defaulted map beside the registered
      branch. A local project's plan reads a worktree with the branch checked out, the main one
      first (`Docs::LocalBranch`, resolved as it opens), else the branch's tip through
      `TreeSource` over the repo itself. `next_over` opens one `Cached` source per distinct
      `Docs`. Every checked write reads the plan's branch under the same lock its check runs
      under (`Proposal::branch`), so no write is judged at a branch a change replaced.

      `Service::fetch` fetches the registered branch, then each plan's branch one at a time; one
      that fails keeps its last tip and is reported as `BranchFetched::Failed`. Setting a branch
      the clone lacks fetches it first under the project's fetch lock. Each branch that moved is a
      `project-fetched` naming that branch and the plans that read it, and `ChangesQuery::follows`
      sends it only to those plans' followers (`Change::reaches`); one from an older service
      names no plans and reaches every plan.

      Tried live on a scratch `reef-serve` on port 12185: data written by the installed
      `reef-serve` (Nov 24, before C87) read back under C92's, its plans, node and queue entry
      intact. Then `reef plan branch p2 b2` followed a `file://` remote's second branch; `p1`
      refused to follow it, since its node linked a doc `b2` lacks; a branch the remote hasn't was
      refused; a node linking `b2`'s doc landed in `p2` and was refused in `p1`; and a push to
      `b2` then `reef project fetch` moved `b2` alone.

  title: C93 The checkout's plan
  status: done
  optional: true
  needs:

  description:
    why: Once a project has several plans, every command, tool and hook with no `--plan` refuses to guess, even in a checkout whose branch only one plan follows.
    what: Commands, MCP tools and hooks with no `--plan` work in the plan the checkout picks, by its loop, its branch or the node its worktree is on, and a refusal names each plan's branch.
    details: |
      `plan_in` (`crates/reef/src/cli.rs`) takes the working directory, and picks the plan named,
      else the only one, else `checkout_plan`'s: the one plan that follows the checkout's branch
      (`branch_plan`; a plan with no branch follows a remote project's registered branch, or the
      branch a local project's main worktree has), else the plan of the node started last in the
      worktree, for a group member's worktree on `reef/<id>`. The branch comes first, so a
      checkout switched to another branch moves to its plan. With nothing picking one, the refusal
      names each plan alone with the branch it follows, the checkout's own branch, and how to name
      one. Every command that picks a plan goes through it, import and export from the book's
      directory, and the MCP tools after C74's loop plan.

      `reef next` and the MCP `next` tool look in the plan picked, and span every plan where
      nothing picks one; `reef next --all` spans them on purpose. The post-commit hook, and the
      no-id paths of `reef node capture`, `reef work` and `reef comment resolve`, take the worktree's
      record in the plan its branch picks (`worktree_record`), so a commit on one plan's branch is
      never drafted into another plan's node. PostToolUse takes a status tool's `plan` alone or in
      full.

# M11 Branches side by side

Optional, once a project has more than one line of work: each plan follows a branch of its
project's repo, its docs read at that branch, and plans worked at once stay apart, each with its
own queue, its own loops and the checkouts on its branch.
