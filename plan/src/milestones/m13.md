    why: Deploying central reef takes about 40 commands over nine pages, needing a nightly toolchain, dx, the wasm target, two sibling checkouts, an account, a unit and a CA copy.
    what: '`reefadm deploy` takes a Linux host with systemd to a healthy team server with its first admin signed in, and `--user` to a localhost user unit, in one command.'
    details: |
      **The binary.** `crates/reefadm`, in the stable workspace, links neither shoal nor Dioxus
      (`tests/tree.rs`): it fetches, builds and installs them through child processes. Every side
      effect goes through `exec::Runner`: probes read even in a dry run, changes are only shown by
      `Dry` and only recorded by `Script`, so `tests/steps.rs` compares a deploy's whole list of
      steps. `Real` runs as the admin and puts `sudo` (or `sudo -u reef`) only before root's steps,
      checking `sudo -n true` first, since `sudo -v` asks for a password a cloud image's
      NOPASSWD user hasn't got. Every child gets `~/.cargo/bin` first on its PATH.

      **Its steps** (`commands/deploy.rs`): preflight (systemd, no record, no unit made by hand,
      free ports, 15 GiB for a first build), the first admin's password, reef at `--ref` and its
      `central/sources.toml`, packages, rustup and toolchains (listed, never `rustup run`, which
      installs a missing one), shoal and glommio at their pinned revs, the three builds with
      `--locked` and a clean environment, a release made current, the account, the config (kept if
      there, refusing flags that disagree, and a `--cores` the data's `shoal-meta.json` doesn't
      have), the unit, reef's CA copied to `/etc/reef/reef-ca.pem`, both ports asked by name, the
      first admin added and signed in, the firewall, and the record last.

      **central/sources.toml** pins shoal and glommio by rev, the nightly
      (`nightly-2026-08-21`), the oldest stable, and `[rewrite]`: glommio's liburing names
      `git://git.kernel.dk`, which serves no https, so it comes from github.com/axboe/liburing.
      `reef-serve version [--json]` prints the schema's id and each table's fingerprint, recorded
      in `reefadm.toml` for C110.

      **Tried live** in a throwaway LXD `ubuntu:26.04` container, from a git bundle of the
      uncommitted tree: a bare image got build-essential, pkg-config and libssl-dev (dx builds
      openssl-sys), rustup, the nightly, the wasm target and dx, then the builds, about 40 minutes
      and 11.6 GiB in all. Four stops along the way were fixed and each run carried on: `sudo -n -v`,
      the container's forwarding (the host's Docker FORWARD policy, the admin's to open), dx's
      openssl headers and kernel.dk's https. From the host, `/api/v1/me` on the TLS port by name
      gave `{"required":true}`, `/` sent a browser to `/sign-in`, and `reef whoami` in the
      container named `ada`, an admin. `deploy --user` over the same checkouts rebuilt in seconds
      and served 127.0.0.1:12180 that a bare `reef whoami` reached, lingering on.

- id: C110
  title: C110 reefadm upgrade and uninstall
  status: done
  needs:
  - C109
  description:
    why: An upgrade is a rebuild, a backup, a reinstall and a restart by hand, and a changed row needs a fresh data directory that nothing detects. Removing reef has no guide.
    what: '`upgrade` refuses a release whose existing tables changed, else builds, backs up, swaps and restarts, rolling back if it doesn''t come up. `uninstall` removes what deploy put, keeping data unless `--purge`.'
    details: |
      **Two halves** (`commands/upgrade.rs`). The admin's reefadm fetches reef at `--ref` (else the
      deployed one), says there's nothing to do at the running release's commits unless
      `--rebuild`, compares the new commit's schema pin (`schema::Schema::from_pin` on
      `central/reef-service/src/schema.rs`) with the tables the running release recorded before
      building anything, builds, has the built `reef-serve version --json` confirm it, and stages
      the release with a `release.toml` saying what it was built from. Then it runs that release's
      own `reefadm upgrade --finish <release>`, so the new code's unit and steps are the ones taken
      (a dry run runs the second half in process, to show it). It stops, backs up
      (`backup::take`: data, clones, certs and the account's `.ssh`, under `umask 077`, with a
      manifest), activates the release, rewrites the unit if it changed, starts and waits for both
      ports. A release that doesn't come up is rolled back: the old release activated, its unit put
      back if it differed, the backup restored over what the new one wrote (kept as
      `*.failed-<time>`), `systemctl reset-failed`, start, health. Then the record keeps the old
      release as `previous`, and `release::prune` removes the rest but any a running process's
      `/proc/*/exe` is in.

      **`schema::Verdict`**: a table added reads back; a table changed or removed refuses, naming
      each and the book's schema-changes page, unless `--fresh`, which moves the data and clones
      aside as `*.<old release>` and starts empty. A release with no recorded tables is said and
      passed, the backup being the way back.

      **`uninstall`** removes the unit, the commands' links (only those into `current`), the
      releases, an empty `/opt/reef`, the CA copy and the record; `--purge` also the data, the
      clones, the certificates, `/etc/reef`, the account with its home and the checkouts (a user's
      config only if reefadm wrote it), naming the backups it kept.

      **Tried live** in the C109 container: N1 put on the team server, then `reefadm upgrade` to a
      later bundle commit rebuilt incrementally, handed over, backed up to a 0600 tarball in a
      0700 `/var/backups/reef`, and served N1 from the new release. An upgrade to a commit whose
      reef-app exits at start waited its 90 s, put the old release back with the backup restored
      and N1 served, the failed data kept aside. `uninstall` kept the config, the data and the
      account, and `deploy` over them kept the config, found ada signed in and served N1.
      `uninstall --purge` left only the two backups.

  description:
    why: Each admin task in the book's Administering chapter is a stop, a command as the right account and a start, typed differently for a system and a user unit.
    what: '`reefadm status`, `logs`, `backup`, `restore` and `recover` do each for whichever unit reefadm deployed.'
    details: |
      Each command picks the deployment as upgrade does (`commands::deployed`: `--user`, else the
      team server, else the user unit) and reads its paths from the deployed config.

      - **`status`** (`commands/status.rs`): the record's release, ref and day; `systemctl show`'s
        state, since and enablement; one `GET /api/v1/me` on each port (`health::asks`, trusting
        `health::trusted`); `du` of the data and clones and `df` beside them; `leaf.toml`'s
        `until`; `LimitMEMLOCK`. A stopped unit or a silent port fails it, naming each.
      - **`logs [-f] [-n N]`**: `journalctl [--user] -u reef.service -b`, as root for a team server.
      - **`backup [--to DIR]`** (`commands/backups.rs`): stop, `backup::take`, then start and
        wait whatever the copy did.
      - **`restore FILE`**: the manifest read first, the question naming a schema the running
        release can't read (`schema::Verdict` of the backup's tables against the record's) or
        another shard count; stop, `backup::restore` moving what is there aside as
        `*.before-restore-<time>`, `reset-failed`, start and wait, saying where each path went.
      - **`recover NAME [--password-file]`** (`commands/recover.rs`): the password read first,
        then stop (unless the store is an external node), `reef-serve recover NAME --conf …
        --password-file -` as the account with the password on its input, start whatever it did,
        and wait.

      **Tried live** on the container's team server, deployed afresh after C110's purge: A1 put,
      `reefadm backup`, B1 put, `reefadm restore`: A1 read back and B1 wasn't in its plan, the
      data before kept aside. `reefadm recover ada` set the password and revoked one token, after
      which `reef whoami` named nobody and `reef login` with the new password named ada an admin.
      `status` exited 0 naming both ports, and with the unit stopped exited 1 naming the unit and
      each port refused; `logs -n 3` showed the journal.

# M13 One command to deploy

Central reef is deployed, upgraded, backed up and removed by one command, `reefadm`, on the host
it runs on or on another over ssh: a team server by default, or one person's user unit.
reefadm fetches and builds reef and its sibling checkouts on the target, as the Deploying
chapter does by hand, and keeps a record of what it deployed for the next upgrade.
