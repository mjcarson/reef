  status: done

  description:
    why: Deploying central reef takes about 40 commands over nine pages, needing a nightly toolchain, dx, the wasm target, two sibling checkouts, an account, a unit and a CA copy.
    what: '`reefadm deploy` takes a Linux host with systemd to a healthy team server with its first admin signed in, and `--user` to a localhost user unit, in one command.'
    details: |
      **The binary.** `crates/reefadm`, in the stable workspace, links neither shoal nor Dioxus
      (`tests/tree.rs`): it fetches, builds and installs them through child processes. Every side
      effect goes through `exec::Runner`: probes read even in a dry run, changes are only shown by
      `Dry` and only recorded by `Script`, so `tests/steps.rs` compares a deploy's whole list of
      steps. `Real` runs as the admin and puts `sudo` (or `sudo -u reef`) only before root's steps,
      checking `sudo -n true` first, since `sudo -v` asks for a password a cloud image's
      NOPASSWD user hasn't got. Every child gets `~/.cargo/bin` first on its PATH.

      **Its steps** (`commands/deploy.rs`): preflight (systemd, no record, no unit made by hand,
      free ports, 15 GiB for a first build), the first admin's password, reef at `--ref` and its
      `central/sources.toml`, packages, rustup and toolchains (listed, never `rustup run`, which
      installs a missing one), shoal and glommio at their pinned revs, the three builds with
      `--locked` and a clean environment, a release made current, the account, the config (kept if
      there, refusing flags that disagree, and a `--cores` the data's `shoal-meta.json` doesn't
      have), the unit, reef's CA copied to `/etc/reef/reef-ca.pem`, both ports asked by name, the
      first admin added and signed in, the firewall, and the record last.

      **Ubuntu 26.04 alone** is what reefadm is made and tested for. On another system, deploy and
      adopt say so from `/etc/os-release` and go on (`deploy::supported`), and no tool's version is
      checked but stable's, since 26.04's git and the rest are new enough.

      **central/sources.toml** pins shoal and glommio by rev, the nightly
      (`nightly-2026-08-21`), the oldest stable, and `[rewrite]`: glommio's liburing names
      `git://git.kernel.dk`, which serves no https, so it comes from github.com/axboe/liburing.
      `reef-serve version [--json]` prints the schema's id and each table's fingerprint, recorded
      in `reefadm.toml` for C110.

      **Tried live** in a throwaway LXD `ubuntu:26.04` container, from a git bundle of the
      uncommitted tree: a bare image got build-essential, pkg-config and libssl-dev (dx builds
      openssl-sys), rustup, the nightly, the wasm target and dx, then the builds, about 40 minutes
      and 11.6 GiB in all. Four stops along the way were fixed and each run carried on: `sudo -n -v`,
      the container's forwarding (the host's Docker FORWARD policy, the admin's to open), dx's
      openssl headers and kernel.dk's https. From the host, `/api/v1/me` on the TLS port by name
      gave `{"required":true}`, `/` sent a browser to `/sign-in`, and `reef whoami` in the
      container named `ada`, an admin. `deploy --user` over the same checkouts rebuilt in seconds
      and served 127.0.0.1:12180 that a bare `reef whoami` reached, lingering on.

- id: C110
  title: C110 reefadm upgrade and uninstall
  status: done
  needs:
  - C109
  description:
    why: An upgrade is a rebuild, a backup, a reinstall and a restart by hand, and a changed row needs a fresh data directory that nothing detects. Removing reef has no guide.
    what: '`upgrade` refuses a release whose existing tables changed, else builds, backs up, swaps and restarts, rolling back if it doesn''t come up. `uninstall` removes what deploy put, keeping data unless `--purge`.'
    details: |
      **Two halves** (`commands/upgrade.rs`). The admin's reefadm fetches reef at `--ref` (else the
      deployed one), says there's nothing to do at the running release's commits unless
      `--rebuild`, compares the new commit's schema pin (`schema::Schema::from_pin` on
      `central/reef-service/src/schema.rs`) with the tables the running release recorded before
      building anything, builds, has the built `reef-serve version --json` confirm it, and stages
      the release with a `release.toml` saying what it was built from. Then it runs that release's
      own `reefadm upgrade --finish <release>`, so the new code's unit and steps are the ones taken
      (a dry run runs the second half in process, to show it). It stops, backs up
      (`backup::take`: data, clones, certs and the account's `.ssh`, under `umask 077`, with a
      manifest), activates the release, rewrites the unit if it changed, starts and waits for both
      ports. A release that doesn't come up is rolled back: the old release activated, its unit put
      back if it differed, the backup restored over what the new one wrote (kept as
      `*.failed-<time>`), `systemctl reset-failed`, start, health. Then the record keeps the old
      release as `previous`, and `release::prune` removes the rest but any a running process's
      `/proc/*/exe` is in.

      **`schema::Verdict`**: a table added reads back; a table changed or removed refuses, naming
      each and the book's schema-changes page, unless `--fresh`, which moves the data and clones
      aside as `*.<old release>` and starts empty. A release with no recorded tables is said and
      passed, the backup being the way back.

      **`uninstall`** removes the unit, the commands' links (only those into `current`), the
      releases, an empty `/opt/reef`, the CA copy and the record; `--purge` also the data, the
      clones, the certificates, `/etc/reef`, the account with its home and the checkouts (a user's
      config only if reefadm wrote it), naming the backups it kept.

      **Tried live** in the C109 container: N1 put on the team server, then `reefadm upgrade` to a
      later bundle commit rebuilt incrementally, handed over, backed up to a 0600 tarball in a
      0700 `/var/backups/reef`, and served N1 from the new release. An upgrade to a commit whose
      reef-app exits at start waited its 90 s, put the old release back with the backup restored
      and N1 served, the failed data kept aside. `uninstall` kept the config, the data and the
      account, and `deploy` over them kept the config, found ada signed in and served N1.
      `uninstall --purge` left only the two backups.

  title: C111 reefadm status, logs, backup, restore and recover
  status: done
  needs:
  - C109
  description:
    why: Each admin task in the book's Administering chapter is a stop, a command as the right account and a start, typed differently for a system and a user unit.
    what: '`reefadm status`, `logs`, `backup`, `restore` and `recover` do each for whichever unit reefadm deployed.'
    details: |
      Each command picks the deployment as upgrade does (`commands::deployed`: `--user`, else the
      team server, else the user unit) and reads its paths from the deployed config.

      - **`status`** (`commands/status.rs`): the record's release, ref and day; `systemctl show`'s
        state, since and enablement; one `GET /api/v1/me` on each port (`health::asks`, trusting
        `health::trusted`); `du` of the data and clones and `df` beside them; `leaf.toml`'s
        `until`; `LimitMEMLOCK`. A stopped unit or a silent port fails it, naming each.
      - **`logs [-f] [-n N]`**: `journalctl [--user] -u reef.service -b`, as root for a team server.
      - **`backup [--to DIR]`** (`commands/backups.rs`): stop, `backup::take`, then start and
        wait whatever the copy did.
      - **`restore FILE`**: the manifest read first, the question naming a schema the running
        release can't read (`schema::Verdict` of the backup's tables against the record's) or
        another shard count; stop, `backup::restore` moving what is there aside as
        `*.before-restore-<time>`, `reset-failed`, start and wait, saying where each path went.
      - **`recover NAME [--password-file]`** (`commands/recover.rs`): the password read first,
        then stop (unless the store is an external node), `reef-serve recover NAME --conf …
        --password-file -` as the account with the password on its input, start whatever it did,
        and wait.

      **Tried live** on the container's team server, deployed afresh after C110's purge: A1 put,
      `reefadm backup`, B1 put, `reefadm restore`: A1 read back and B1 wasn't in its plan, the
      data before kept aside. `reefadm recover ada` set the password and revoked one token, after
      which `reef whoami` named nobody and `reef login` with the new password named ada an admin.
      `status` exited 0 naming both ports, and with the unit stopped exited 1 naming the unit and
      each port refused; `logs -n 3` showed the journal.

  title: C112 reefadm --host
  status: done
  needs:
  - C109
  description:
    why: The server is usually another machine, and deploying it means logging in to it first.
    what: Any reefadm command runs on another host over ssh, its prompts on the local terminal.
    details: |
      `reefadm --host HOST …` (`remote.rs`) runs on HOST with every argument but `--host`
      (`remote::forwarded`), each quoted for its shell (`remote::line`), through the system's
      `ssh`, so `~/.ssh/config`, the agent and ProxyJump apply.

      - **Reached:** `ssh -o BatchMode=yes HOST -- uname -sm; echo $HOME` first, refusing a host
        that asks for ssh's own password.
      - **The copy:** where HOST is this host's system, this binary is sent over ssh's input to
        `~/.cache/reefadm/reefadm` when its sha256 differs, renamed into place whole, and probed
        with `--version`.
      - **Refused** when the copy can't run there (another architecture, an older glibc), saying
        why from the probe's last line, since ssh's own warnings come first. A fallback that built
        reefadm there with rustup and `cargo install` came first, and went in C115, once a release
        is built where reefadm is typed and only reefadm's plain-x86-64 copy runs on the target.
        C115 also routes `deploy`, `deploy --adopt` and `upgrade` through a build here.
      - **The command:** `ssh [-t] HOST -- reefadm …` through `Runner::interact`, with a terminal
        when this one has one, for sudo's prompts and reef's; its exit code comes back through
        `Exit`, which `main` exits with silently.
      - **`--password-file`** is read here, sent under `umask 077` to
        `~/.cache/reefadm/password-<pid>` there, swapped into the arguments, and removed however
        the command ended.

      **Tried live:** from this host in a tmux pane, `reefadm --host ubuntu@CONTAINER deploy` took
      the ubuntu:26.04 container to a team server with its first admin signed in, sudo-rs's
      prompt and the admin's password answered here; `status` over `--host` exited 0, and 1 with
      the unit stopped. On ubuntu:22.04 the copy ran despite wanting a newer glibc. On
      ubuntu:20.04 (glibc 2.31) it didn't, and reefadm installed build-essential and rustup there,
      built itself in 11 s, and ran, stopping on that host's git 2.25 with its exit code 1 passed
      back. That run showed ssh's post-quantum warning as the reason, so the reason is now the
      probe's last line.

- id: C113
  title: C113 Taking over a hand-made install
  status: done
  needs:
  - C110
  - C111
  description:
    why: Servers set up by the Deploying chapter by hand, europa's among them, have no reefadm state, so `reefadm upgrade` can't move them.
    what: '`reefadm deploy --adopt` takes over a system or user install made by hand, keeping its config and data after a backup, and puts it back as it was if the new release doesn''t come up.'
    details: |
      `reefadm deploy [--user] --adopt [--from-rev REV]` (`commands/adopt.rs`) takes over reef
      installed by hand, as the Deploying chapter does it.

      - **Found as systemd loads it** (`adopt::find`): `systemctl show reef.service` for its
        LoadState, FragmentPath, DropInPaths, ExecStart, User, Environment, ActiveState and
        UnitFileState. Refused before anything changes: no unit, one reefadm wrote (`reefadm
        upgrade`), a team unit not run as `reef` with its home at `/var/lib/reef`, and a program
        that is neither reef-app's `server` beside its `public/` nor `reef-serve`.
      - **Its config** is `--conf`, else `REEF_CONFIG=`, else the default under that home. Each path
        it leaves out is filled in as reef fills it, under the unit's `XDG_DATA_HOME` or
        `~/.local/share`. It is kept as it is unless reefadm wouldn't read it the same: one
        elsewhere, or one leaving a path whose default reefadm's unit moves. That one is written
        where reefadm reads it, every key kept and those paths named (`Found::rewritten`), the
        file there kept as `config.toml.before-reefadm`.
      - **Its schema:** `--from-rev`'s pin, else the old reef-serve's `version --json`, since every
        reef-serve back to the first refuses an argument it doesn't know. It is checked against
        the new commit's pin before the build and the built reef-serve's after it. When it is
        unknown, adopt says so and relies on its backup.
      - **Kept, after the build:** stopped, backed up as release `adopted`, the layout's commands
        and the app's directory copied with `cp -a` into `releases/adopted`, which pruning keeps,
        and the unit copied to `reef.service.before-reefadm`. Then the new release is made current,
        reefadm's unit written and enabled, and both ports asked.
      - **Put back** on any failure from there (`put_back`, from what `Kept` recorded): the unit
        moved back, or reefadm's removed when systemd loaded one from elsewhere; each command copied
        back over its link with `--remove-destination`, and those it lacked removed; the config
        moved back; the backup restored if the new release ran; `reset-failed`; disabled again if
        it was; started again if it was running.
      - **Plain HTTP:** an install that answers `http://` on loopback, as reef did before C87, is
        told its clients need `https://` and reef's CA.
      - **The record:** the new release, the adopted install as `previous` with its tables. The
        summary leaves out `reef project add`, since it has its projects.

      **Tried live** in the ubuntu:26.04 container: reefadm's deploy there uninstalled, its data
      kept, then reef installed by hand from its checkout as build.md, config.md and systemd.md
      give it, serving project `held`'s H1. From this host, `reefadm --host … deploy --adopt` found
      it, read its schema from the hand-made reef-serve, built, backed it up, kept its unit,
      commands and app, and swapped in reefadm's unit: H1 read back, `status` exited 0 on both
      ports, and the config was as written by hand, comments and all.
      `reefadm upgrade` then moved it to a later commit through the new release's `upgrade
      --finish`, H1 still read back on both ports, and pruning kept `adopted`.

      **After a dry run against europa's own install,** three fixes. A config is written by adding
      a line under each table's header (`adopt::with_key`), so its keys and comments stay as they
      were, and adopt refuses when that wouldn't parse. The unit's own settings that reefadm's
      lacks, europa's `Slice`, `WorkingDirectory`, `CPUAffinity`, `AllowedCPUs`, `MemoryHigh` and
      `MemoryMax` among them, go into `reef.service.d/adopted.conf` with the comments above each
      (`adopt::carried`), and are removed again if the install goes back. The unit is written once,
      by deploy's start.

- id: C115
  title: C115 Built here for the target, shipped there
  status: done
  needs:
  - C112
  - C113
  description:
    why: reefadm builds on the server, which then needs rustup, a nightly, dx and 15 GiB, and a `-Ctarget-cpu=native` build is only safe on the machine that made it.
    what: reefadm probes the target's CPU features, builds a release for exactly those on the machine it runs on, and ships it, so a server needs only Ubuntu 26.04, systemd and sudo.
    details: |
      reefadm builds where it is typed, for the target's CPU, and ships the release there, so a
      server needs only Ubuntu 26.04, systemd and sudo.

      - **Features, not models** (`cpu.rs`). reefadm's copy on the target, built for plain x86-64,
        asks its CPU through `is_x86_feature_detected!`, plus LAHF/SAHF from CPUID leaf
        0x8000_0001, which std doesn't detect. `Class::of` takes what the target and the builder
        both have, since the flags reach build scripts and the built reef-serve runs here, and
        names what it dropped. It refuses a CPU without aes or sse2, which gxhash needs. The flags
        are `-C target-cpu=x86-64-vN`, the highest psABI level both reach, plus `+f` for each other
        feature the nightly lists in the first section of `--print target-features`.
        `--target-cpu` overrides the probe; the class's directory is `cpu-<level>-<fnv64>`.
      - **Builds** (`compile.rs`). The central builds get the flags in
        `CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUSTFLAGS`, for the host triple alone, so the wasm
        client never gets them, and `CARGO_TARGET_DIR` per class. The root build stays generic.
        Afterwards the newest fingerprint of each server is read back, and a release whose last
        `-C target-cpu` isn't the class's is refused. The three most recent classes are kept.
      - **Halves.** deploy, adopt and upgrade each swap their fetch-and-build for hidden
        `--shipped D`: the record from `D/release.toml` (and `D/adopted.toml`), the files staged
        through `release::stage`. A hidden `--facts` says what a builder needs, as one JSON line:
        `ship::Facts`, with the CPU's features, OS, admin, reefadm's record, and the problems found
        without root.
      - **`--host`** (`commands/hosted.rs`). Copy reefadm there, refusing a copy compiled with
        anything beyond plain x86-64 (`cpu::compiled`); ask its facts; fetch, prepare and build
        here; stage into `~/.local/share/reefadm/out`; ship with one `tar | ssh` step into
        `~/.cache/reefadm/shipped`; install with the copy over `ssh -t`, a command line built here
        so `--src`, `--repo` and `--ref` never go; remove what was shipped. A dry run still copies
        and asks, through `Runner::real`. Other commands run there as before. The fallback build
        there is gone.
      - **On the target**, `--shipped` refuses a release whose reef-serve `version --json`
        `features`, new here, include one the CPU lacks.
      - **The shoal pin moved.** shoal's `ScanSupport` was rewritten on 2026-11-27 to drop its
        benchmark data, which took `dbfb82e` off the branch. The pin is now `e40b08f`, the same code
        (6,048 deletions under `*/results`, nothing else), as europa2's
        `shoal-benchmarks/reef-pin-map.md` maps it. A pinned commit a branch no longer holds is now
        fetched by itself, and reefadm says so.

      **Tried live**, from this host (Ryzen 9 9950X) with reefadm built with `RUSTFLAGS` unset. A
      fresh ubuntu:26.04 container with no cargo, rustup, rustc or dx was deployed with `--host`:
      built here for `x86-64-v4` and the 22 features both CPUs have, shipped as one tar,
      installed by the copy, the first admin added and signed in, and `status` exited 0 on both
      ports. The fingerprints showed `-Ctarget-cpu=native` from central's config, then the class
      for both servers, dx's included, and the wasm client without it. reef-serve's 45 compiled
      features were all in the container's `/proc/cpuinfo`. Then it was upgraded to a later commit,
      and again to `--target-cpu x86-64-v2`. That release's reef-serve said only the v2 features
      and aes, its server had 106,673 ymm/zmm instructions (runtime-dispatched code in
      dependencies) against the v4 build's 661,673, and `status` stayed 0. Against europa2 (Ryzen 9
      7945HX), `--dry-run deploy --adopt --from-rev 3546826` built for europa's own features,
      without the avx512vp2intersect and avxvnni it lacks, named rdseed as left out (this host's
      kernel masks it on Zen 5), shipped, and ran the install's dry run there.

# M13 One command to deploy

Central reef is deployed, upgraded, backed up and removed by one command, `reefadm`, on the host
it runs on or on another over ssh: a team server by default, or one person's user unit.
reefadm fetches and builds reef and its sibling checkouts on the target, as the Deploying
chapter does by hand, and keeps a record of what it deployed for the next upgrade.
