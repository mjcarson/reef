    description:
      why: "A batch is written one row at a time, so a process killed partway leaves a group with only some of its members."
      what: "A batch of several puts and removals lands whole or not at all, and nodes it doesn't touch keep their versions. One put or one removal is still a single row's write."
      details: "`Store::batch_checked`, after its stale check and its check, writes one put or one removal in place (`Store::write_one`): a single conditional write or delete, which shoal makes atomic. A batch of more goes through `Store::rewrite`, as `write_plan` does: a revision reserved as `pending`, its rows written in bundles, made current by one conditional write to the plan's row, and the old one pruned. Its rows are the plan as the batch leaves it, each node it doesn't touch at the version it was at, each put one on from the version read, and each removal left out. `rewrite` now takes each node's version from its caller, and `write_plan` still moves every node's on. A batch killed before the flip leaves the plan as it was, and the next write prunes what it wrote. Cost, from X2's figures for 202 nodes: a 2.2 ms write and a 2.0 ms prune, under the plan's lock, against 0.15 ms a put in place; unmeasured here. A several-node batch moves the plan's revision on, which `Listing.revision` shows."

# M3 One service, two front doors

One service layer owns shoal and the model. Two front doors call it: the JSON API, for the CLI,
the MCP server and the hook, and the app's server functions ([M4](m4.md)). The CLI and the MCP
tools are what the terminal loop runs on, so this milestone does not wait for the app.
