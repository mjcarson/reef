  title: C48 Users and sign-in
  status: done
  optional: true
  needs:
  - C13
  docs:
  - ../design/architecture.md#users-and-sign-in
  description:
    why: Beyond one machine, reef can't tell who is editing, and anyone who reaches its port can write.
    what: Users sign in, and one axum layer guards both the app and the JSON API, when reef's config requires it.
    details: |
      `[auth] required = true` turns sign-in on; off, the default, every caller is answered as
      before, so reef's own unit runs with no login. `reef_service::auth::guard` wraps reef-serve's
      JSON API and reef-app's whole router, finds the caller from `Authorization: Bearer` or the
      `reef_sign_in` cookie, and hands each route a `Caller`. With sign-in on, everything but the
      sign-in routes, `/api/v1/me`, the users' routes and static files needs a user: a page a browser
      opens is sent to `/sign-in?next=…`, anything else answered 401.

      Users and tokens are two new tables, `UserRow` and `TokenRow`, a password kept as its argon2id
      hash and a token as its SHA-256. `POST /api/v1/tokens` issues a token, `DELETE
      /api/v1/tokens/current` revokes it, and `GET`/`POST /api/v1/users` list and add users: the first
      from the service's own host, as an admin, then by an admin. `reef login`, `logout`, `whoami`,
      `user add` and `user ls` speak them; a login keeps its token in
      `$XDG_CONFIG_HOME/reef/credentials.toml`, mode 0600, which every `reef` reads for each request,
      or `--credentials`, `$REEF_TOKEN` or `$REEF_CREDENTIALS`. The browser signs in on a plain HTML
      page the service serves, which sets an HttpOnly, SameSite=Strict cookie, and the app's bar
      says whom it is signed in as, beside a Sign out.

      Tried live with a scratch `reef-serve` on its own port: a data directory the binary before C48
      wrote read back under C48's with sign-in on; anonymous reads and puts were refused, naming
      `reef login`; then `reef user add`, `reef login`, a put, `whoami` and `reef logout`, after
      which a put was refused again. Thirteen tables overflowed a shoal shard's 2 MiB stack in debug
      builds, so the servers and `cargo test` now set `RUST_MIN_STACK` to 8 MiB. Known limits, for
      C51 and C77: sign-in is not rate-limited, cookies ignore ports so another loopback port is
      same-site and no origin is checked, an open change stream outlives its token's revoke until it
      reconnects, and while reef has no user another OS user on the same host could add the first.

- id: C49
  title: C49 Projects from remote repos
  status: done
  optional: true
  needs:
  - C14
  docs:
  - ../design/store.md#remotes
  description:
    why: A shared server has no local checkout of each user's repo to read docs from.
    what: A project registers by its git URL, and reef fetches its own clone, on request and on an interval, to read docs at the commit it fetched. A node's changes still arrive from the capture hook on the user's machine.
    details: |
      `reef project add <name> --url <URL> [--branch B]` (`NewProject`'s `remote`) registers a
      project by its git remote. The service checks the URL first (`remote::checked`, through
      gix-url): file, git, ssh, http or https only, so `ext::` and remote helpers are refused, and so
      are a password, any user over http(s), a relative path, and a host or path git would read as
      an option. It then makes a bare clone of its own under `[remotes] clones` (`<name>.<ms>.git`)
      with `git init --bare`, and fills it with the shallow, one-branch fetch that every later fetch
      runs too. The URL is never kept in the clone. A `RemoteRow` beside the project's row keeps the
      URL, the branch, the clone's path and the commit fetched. The project's row keeps the clone's
      path where a local project keeps its repo's. That made it a new table, not a changed row, so no
      fresh data directory was needed. Docs are read from git's objects at the commit the row keeps
      (`tree::TreeSource` over gix, behind `tree::Docs` at every read site). Symlinks are followed
      only while they stay in the tree, so every read of one moment sees one commit.

      Fetching is `reef project fetch` (`POST …/projects/{project}/fetch`, answering `Fetched`), or
      `[remotes] fetch_every` (default 5m, `0s` for never), which `Service::follow_remotes` runs
      beside the routes in reef-serve and reef-app. A branch that moved is `project-fetched`. It
      reaches every follower of the project's plans (`Change::reaches_every_plan`), and the app
      reloads its plan and queue on it. Every `reef` sends its checkout's remote URLs with
      `find-project`, users and passwords stripped, and the service matches them by host and path
      (`remote::key`). So a user's clone finds the project, and `reef start`, `node capture`, the
      hooks and the MCP tools work there. A `dir` not on the service's host is no longer a 400.

      Tried live on a scratch `reef-serve` on its own port:
      - a data directory the binary before C49 wrote read back under C49's;
      - a `file://` remote registered and was cloned;
      - a link to a section pushed later was refused, then accepted within 15 s with `fetch_every =
        "5s"` and no fetch asked for;
      - a node was started and captured from a user's clone.

      Known limits:
      - clones are never removed, since projects can't be;
      - moving `[remotes] clones` strands the paths kept;
      - a doc kept in LFS reads as its pointer, and a submodule's docs aren't read;
      - a link to a doc not yet pushed and fetched is refused;
      - until C51, anyone who reaches the API can have the service clone any repo its account can read.

- id: C51
  title: C51 Served beyond localhost
  status: done
  optional: true
  needs:
  - C48
  docs:
  - ../design/architecture.md#served-beyond-localhost
  description:
    why: The server binds to localhost only, with no TLS and no origin or CSRF checks, and anyone who reaches it can have it read or clone what is on its host.
    what: reef serves other hosts over TLS beside its loopback port, every write from a browser is checked for its origin, and only an admin registers what is on the service's host.
    details: |
      `[api] address` stays plain HTTP on loopback, for this host's CLI, hooks, MCP server and first
      admin. `[api.tls]` (an address, a PEM chain and its key) adds a listener over TLS on any
      address, which `tls::bind` refuses unless `[auth] required` is set. `tls::TlsListener` is an
      `axum::serve::Listener` over tokio-rustls and ring that hands axum a connection once its
      handshake is done, each handshake a task of its own, at most 128 at once, under 10 s.
      `api::serve_router` serves one router on both listeners under one stop, for reef-serve and
      reef-app alike, and each request carries an `auth::Peer`: the address it came from, so the
      first user still comes from a loopback peer alone, and whether it came over TLS, so the
      sign-in cookie, set and cleared, is `Secure` there.

      Every write is judged by `origin::judge` in the guard, with sign-in on or off, as Go's
      `CrossOriginProtection` judges it: a `Sec-Fetch-Site` of `same-origin` or `none` goes on and
      any other is refused 403; without one, an `Origin` must name the connection's scheme and the
      host and port the request was sent to. A request with neither, as the CLI's, goes on, and so
      does every read. No CSRF token: the check covers the JSON API, the app's server functions,
      whose decoder reads a body of any content type, and the sign-in and sign-out forms.

      With sign-in required, registering a project by a directory on the service's host, or by a
      remote naming a path there (`file://` or bare), takes an admin (`Service::judge_on_host`),
      judged before the path is looked at. `[remotes] hosts`, if set, names the only hosts a remote
      may be cloned from, for every caller. The CLI calls `[api] url` over TLS when the config names
      one, trusting `[api] ca` beside the system's roots, keeps its login by that root, and says the
      service isn't running only for a connection refused, giving every cause otherwise, a refused
      certificate among them.

      Tried live on a scratch `reef-serve` with TLS on `0.0.0.0`: the first user asked for over TLS
      from the host's LAN address was refused, then added over loopback; a `reef` on `url` by the
      host's name signed in, registered, put and read; puts naming another origin, port or scheme
      were refused 403 and the service's own origin applied; a user who isn't an admin was refused a
      directory, `/etc` and `file:///etc`; a remote off `hosts` was refused. openssl's default
      self-signed certificate is a CA, which rustls refuses as a server's own, so the README says to
      make it a leaf. Known limits: a renewed certificate is read at the next restart; no HSTS; no
      reverse proxy's forwarded headers; and DNS rebinding onto the plain port with sign-in off,
      which is C80's.

- id: C77
  title: C77 Managing users and tokens
  status: done
  optional: true
  needs:
  - C48
  docs:
  - ../design/architecture.md#managing-users-and-tokens
  description:
    why: C48 adds users and their tokens, but a password can't be changed, a user can't be removed, a token can't be listed or revoked but by its own logout, and sign-in isn't rate-limited.
    what: Users change their passwords and list and revoke their tokens, admins set others' passwords and remove users, the service's host recovers a lost admin, and repeated failed sign-ins are slowed.
    details: |
      Tokens are listed by an id, the first 16 hex digits of their SHA-256: `GET /api/v1/tokens`
      (the caller's, the one sent marked `current`, or `?user=` an admin names) and
      `DELETE /api/v1/tokens/{id}`, 404 for an id the caller may not see. `PUT
      /api/v1/users/{name}/password` changes the caller's own with its `current`, keeping their
      tokens, or another's by an admin, revoking theirs; `DELETE /api/v1/users/{name}` removes a user
      and their tokens, never the last admin (409). The CLI speaks them as `reef user passwd [NAME]`,
      `reef user rm NAME`, `reef token ls [--user NAME]` and `reef token revoke ID… | --others`, and
      the app as an account page at `/account`, linked from the bar's name.

      `service/throttle.rs` slows failed sign-ins by name (5 free) and by address (20 free, IPv6 by
      /64): then waits from 1 s doubling to 5 min, answered 429 (`too-many-tries`, `Retry-After`)
      before any hash, each try counted as it is let through and a success taking it back. It covers
      the token route, the sign-in form and one's own password change. A token issued before its
      user's `created_at` signs nobody in, so a reused name inherits nothing. Each revoke bumps a
      `watch` counter that `Service::signed_out` waits on, which `/api/v1/changes` takes its stream
      until, with sign-in required.

      `reef-serve recover NAME [--password-file PATH] [--conf PATH]` opens the store itself and
      calls `Service::recover_admin`: a new password, an admin, the user's tokens revoked, or a new
      admin; it says to stop the service when shoal's data directory is held. The terminal prompt
      moved to `reef_api::prompt` behind a `prompt` feature, shared by the CLI and reef-serve.

      Tried live on a scratch `reef-serve` over data the binary before C77 wrote (no table or row
      changed): passwords, `--others`, a change stream ending 16 ms after its token's revoke, a 429
      after five wrong logins, removal, and recovery refused while running then applied after.
      Known limits: the throttle is in memory, so a restart forgets it; it reads no reverse proxy's
      forwarded address; and an expired browser token ends its stream at the next minute's look.
