  title: C48 Users and sign-in
  status: done
  optional: true
  needs:
  - C13
  docs:
  - ../design/architecture.md#users-and-sign-in
  description:
    why: Beyond one machine, reef can't tell who is editing, and anyone who reaches its port can write.
    what: Users sign in, and one axum layer guards both the app and the JSON API, when reef's config requires it.
    details: |
      `[auth] required = true` turns sign-in on; off, the default, every caller is answered as
      before, so reef's own unit runs with no login. `reef_service::auth::guard` wraps reef-serve's
      JSON API and reef-app's whole router, finds the caller from `Authorization: Bearer` or the
      `reef_sign_in` cookie, and hands each route a `Caller`. With sign-in on, everything but the
      sign-in routes, `/api/v1/me`, the users' routes and static files needs a user: a page a browser
      opens is sent to `/sign-in?next=…`, anything else answered 401.

      Users and tokens are two new tables, `UserRow` and `TokenRow`, a password kept as its argon2id
      hash and a token as its SHA-256. `POST /api/v1/tokens` issues a token, `DELETE
      /api/v1/tokens/current` revokes it, and `GET`/`POST /api/v1/users` list and add users: the first
      from the service's own host, as an admin, then by an admin. `reef login`, `logout`, `whoami`,
      `user add` and `user ls` speak them; a login keeps its token in
      `$XDG_CONFIG_HOME/reef/credentials.toml`, mode 0600, which every `reef` reads for each request,
      or `--credentials`, `$REEF_TOKEN` or `$REEF_CREDENTIALS`. The browser signs in on a plain HTML
      page the service serves, which sets an HttpOnly, SameSite=Strict cookie, and the app's bar
      says whom it is signed in as, beside a Sign out.

      Tried live with a scratch `reef-serve` on its own port: a data directory the binary before C48
      wrote read back under C48's with sign-in on; anonymous reads and puts were refused, naming
      `reef login`; then `reef user add`, `reef login`, a put, `whoami` and `reef logout`, after
      which a put was refused again. Thirteen tables overflowed a shoal shard's 2 MiB stack in debug
      builds, so the servers and `cargo test` now set `RUST_MIN_STACK` to 8 MiB. Known limits, for
      C51 and C77: sign-in is not rate-limited, cookies ignore ports so another loopback port is
      same-site and no origin is checked, an open change stream outlives its token's revoke until it
      reconnects, and while reef has no user another OS user on the same host could add the first.

- id: C49
  title: C49 Projects from remote repos
  status: done
  optional: true
  needs:
  - C14
  docs:
  - ../design/store.md#remotes
  description:
    why: A shared server has no local checkout of each user's repo to read docs from.
    what: A project registers by its git URL, and reef fetches its own clone, on request and on an interval, to read docs at the commit it fetched. A node's changes still arrive from the capture hook on the user's machine.
    details: |
      `reef project add <name> --url <URL> [--branch B]` (`NewProject`'s `remote`) registers a
      project by its git remote. The service checks the URL first (`remote::checked`, through
      gix-url): file, git, ssh, http or https only, so `ext::` and remote helpers are refused, and so
      are a password, any user over http(s), a relative path, and a host or path git would read as
      an option. It then makes a bare clone of its own under `[remotes] clones` (`<name>.<ms>.git`)
      with `git init --bare`, and fills it with the shallow, one-branch fetch that every later fetch
      runs too. The URL is never kept in the clone. A `RemoteRow` beside the project's row keeps the
      URL, the branch, the clone's path and the commit fetched. The project's row keeps the clone's
      path where a local project keeps its repo's. That made it a new table, not a changed row, so no
      fresh data directory was needed. Docs are read from git's objects at the commit the row keeps
      (`tree::TreeSource` over gix, behind `tree::Docs` at every read site). Symlinks are followed
      only while they stay in the tree, so every read of one moment sees one commit.

      Fetching is `reef project fetch` (`POST …/projects/{project}/fetch`, answering `Fetched`), or
      `[remotes] fetch_every` (default 5m, `0s` for never), which `Service::follow_remotes` runs
      beside the routes in reef-serve and reef-app. A branch that moved is `project-fetched`. It
      reaches every follower of the project's plans (`Change::reaches_every_plan`), and the app
      reloads its plan and queue on it. Every `reef` sends its checkout's remote URLs with
      `find-project`, users and passwords stripped, and the service matches them by host and path
      (`remote::key`). So a user's clone finds the project, and `reef start`, `node capture`, the
      hooks and the MCP tools work there. A `dir` not on the service's host is no longer a 400.

      Tried live on a scratch `reef-serve` on its own port:
      - a data directory the binary before C49 wrote read back under C49's;
      - a `file://` remote registered and was cloned;
      - a link to a section pushed later was refused, then accepted within 15 s with `fetch_every =
        "5s"` and no fetch asked for;
      - a node was started and captured from a user's clone.

      Known limits:
      - clones are never removed, since projects can't be;
      - moving `[remotes] clones` strands the paths kept;
      - a doc kept in LFS reads as its pointer, and a submodule's docs aren't read;
      - a link to a doc not yet pushed and fetched is refused;
      - until C51, anyone who reaches the API can have the service clone any repo its account can read.
  acceptance:

- id: C51
  title: C51 Served beyond localhost
  optional: true
  needs:
  - C48
  description:
    why: The server binds to localhost only, with no TLS and no origin or CSRF checks.
    what: reef serves over TLS to other hosts, with origin and CSRF checks on every write.
    details: |
      From C48: the sign-in cookie is HttpOnly and SameSite=Strict but not Secure, since nothing is
      served over TLS yet; it gains Secure here. Cookies ignore ports, so a page served from another
      port of the same loopback host is same-site and its form posts carry the cookie: the origin
      checks close that. The first user is accepted only from a loopback peer, which matters once
      reef binds beyond loopback.

      From C49: anyone who reaches the API can register a project for any directory on the
      service's host (`--repo`), or by any URL its account can fetch, a `file://` one among them, so
      the service reads or clones what they name. Once reef binds beyond loopback, a local `repo` and
      a `file://` remote should be an admin's to register, and a remote's host may want an allowlist.
  acceptance:
  - feature: A cross-origin write is refused
