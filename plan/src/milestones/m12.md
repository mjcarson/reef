- id: C102
  title: C102 Test runs told to central
  status: done
  docs:
  - ../design/code-and-comments.md#test-runs
  description:
    why: central reef has no route, change or view for a test run, so how far a node's tests have got is known only in the terminal running them.
    what: A client opens a run on a project, and a node if its checkout is on one, reports each binary's counts and each failure's output, and the service keeps runs in memory and tells each change.
    details: |
      **The types.** `reef_api::test_run` holds `TestRun`, `OpenRun`, `RunReport`, `Binary`,
      `BinaryState`, `FailedTest` and `RunState`. A run names its client's id, its project, and the
      plan and node of its checkout if it is on one, its host, checkout and command. Each report
      gives every `Binary` whole (package, cargo's target, total, whether the total is guessed, its
      passed, failed and ignored counts, its state, and its start and end) and the failures since
      the last. Times are milliseconds since the run's start by the client's clock, and the
      service anchors `started_at` to its own clock as `now - elapsed_ms`, so clock skew between
      hosts never mistimes a binary. `TestRun` counts `total`, `done`, `left` and `not_run`, where
      a binary cargo won't run counts as not run rather than left. `RunState::Gone` is derived by
      `TestRun::at`, past `RUN_GONE_AFTER_MS`, as a session's is.

      **The service.** `service/test_runs.rs` keeps a `Held` of runs by id, and of each project's
      last run of each command that finished passed or failed, which C104 estimates from
      (`Service::last_test_run`). A project keeps its latest `KEPT_RUNS` (32), letting go of the
      oldest that ended or went silent, never a live one, and `KEPT_COMMANDS` (64) commands. A run
      keeps its first `KEPT_FAILURES` (200) failures, each output cut to its last `OUTPUT_MAX`
      (8,000) characters, where the panic is. A run that ended stays ended. Each open and report is
      a `Change::TestRunChanged` naming the run and its plan; one on no node `reaches` every plan.

      **The routes.** `POST /api/v1/test-runs` opens (400 for a bad id, a node with no plan or not
      in it, or no command; 404 for a project or plan not there), `GET` and `POST
      /api/v1/test-runs/{run}` read and report (404 for a run not held, `NoTestRun`), and `GET
      /api/v1/projects/{project}/test-runs` lists newest first with each failure's output left
      out. The CLI's `Client` has `open_test_run`, `report_test_run` (`None` on a 404, so the
      client opens again), `test_run` and `project_test_runs`. `docs/src/internals/test-runs.md`
      describes them.

  title: C103 reef test wraps cargo test
  status: done

  description:
    why: Reporting a run needs something to read cargo's output as it comes, without asking the tested repo to change or to know of reef.
    what: '`reef test [ARGS]` runs `cargo test [ARGS]` as given, its output unchanged and its exit code cargo''s, knows the total before a test runs, and reports to central where it answers.'
    details: |
      **The command.** `reef test [ARGS]` (`crates/reef/src/test_run`) takes every argument after
      `test` as typed: clap takes a leading `--`, so `Cli::from_args` and `Cli::parse_args` put the
      raw tail back. It is dispatched before the config is read, so a broken config can't stop the
      tests, and it exits with cargo's code through `reef::Exit`, or ends by the signal that ended
      cargo through `reef::Killed`, so a shell's Ctrl-C stops a loop of them as it would cargo's.

      **Built and listed first.** `cargo test <cargo's args> --no-run --message-format=json`
      builds; each `compiler-artifact` built as a test is listed with `--list --format terse` and
      libtest's arguments (less `--format`, `-q`, `--logfile`, `--color`, `--list`) as soon as it
      is built, from its package's directory, with a 10 s limit. A target its manifest gives
      `harness = false` is never run to list it. Each lib with doc tests gets a binary of them,
      guessed from the project's last finished run of the same command (`project_test_runs`)
      until their `running N tests`. Binaries are ordered as cargo sorts them (package, kind,
      name), and one cargo runs out of turn moves just after those that ran, so a failure's index
      never changes. The build is skipped for `--no-run`, `--doc` and a user's `--message-format`.
      The build's stderr is shown but for its `Executable` lines and errors, which the run says
      again (`cargo::Quieted`); its `Finished` line is kept and shown in place of the run's own,
      so the time is the build's and the run's replayed warnings still come first.

      **A pty where a terminal watches** (`Mode::detect`: stdout and stderr both terminals): one
      pty for both streams, sized as the terminal and resized on SIGWINCH, OPOST off so bytes
      pass as written, read through tokio's `AsyncFd`; no session of its own, so Ctrl-C reaches
      cargo as ever. Elsewhere, as under Claude's Bash tool, a pipe each, to reef's own stdout and
      stderr. Interrupt, terminate and hangup are passed on to cargo. A 300 ms grace ends the read
      once cargo has exited, should something it started hold a stream open.

      **Reading** (`libtest::Tally`, pure): lines as a terminal shows them (CSI, OSC links,
      charset escapes and a carriage return's overdrawn text gone). cargo's `Running` (matched by
      the executable's file name) and `Doc-tests`, `error: test failed`; libtest's `running N
      tests`, each test's line, `failures:` blocks (not `successes:`), the failed names list and
      `test result:`, whose counts have the last word. With `--nocapture` a failure's output is
      what it printed before its `FAILED`. Through pipes, a libtest line waits for cargo to name
      its binary and an announcement waits for the running binary's result; a fresh `running N`
      while one is owed means that binary died. A quiet cargo (`-q`) names no binary, so each
      `running N` takes the next in turn.

      **Reporting** (`report.rs`) runs beside the tests on the same task: config, project
      (`find_project`), node (`cli::worktree_record`, as `reef work`), then `open_test_run` with
      id `run::runner_id()`. Any failure before the open is said once on stderr. Reports go on
      each change, at most one per 500 ms and at least one per 15 s, with the failures since the
      last that went; a 404 reopens with everything held; the last report gets 3 s.

      **Tried live** on a private tmux server, `cargo test` and `reef test` side by side: the
      scratch crate's screens matched byte for byte, colours included, but for reef's one notice
      line; a cold `-p reef-api` build showed the progress bar and the same lines, its `Finished`
      timed as cargo's; Ctrl-C ended both alike (`$?` 130, the rest of the command line dropped).
      Against europa, whose server predates C102, the open got a 405, said once, and the tests
      ran.

# M12 Test runs followed live

A node's test run is followed from central reef as it goes: how many tests are done and left,
when the run should be done, and which tests failed and why, on the node its checkout is on.
The tested repo doesn't change, and `cargo test` runs as before where reef isn't reachable.
