# F146. SHQL's `SCAN`, shoalctl's paging, the bench's client scan and the example

A client could scan a table by its typed `{Row}Scan`. Text could not: SHQL had `SELECT`, which
requires a partition key, so shoalctl could not show a table, and the bench's driver read a table
whole only as an administrator, through the admin walk.

Now `SCAN <table> [WHERE <filter fields>] [LIMIT n]` is a statement of its own. A schema parses it
into a scan with its row type erased, the client drives it through the same driver a typed scan
uses, shoalctl shows it a page at a time, the bench's driver can read a table as an ordinary client
does, and the example reads its rows back with one.

```sql
SCAN Movie WHERE year IN (1979, 1982) LIMIT 100;
```

## Context

[W10](../future-work/scans/api.md#shql-and-shoalctl) is the design. The driver is
[F145](scan-driver.md)'s and the rows body [F143](scan-rows.md)'s. This is the seventh and last
build step of [M24](../future-work/scans/whats-left-todo.md#finishing-m24); what is left of the
gate is its exit.

## What it does

### The statement

`ParsedScan::new` (`shoal-proto/src/shared/queries/parser.rs`) parses

```text
SCAN <table> [WHERE <condition> [AND <condition>]...] [LIMIT <n>] [;]
```

with `SELECT`'s own condition and limit parsers. The `WHERE` clause is optional: a scan with none
reads every row. `parser::is_scan` says whether a statement begins with the keyword.

`QuerySupport::parse_scan`, generated by `#[shoal::db]`, binds it to a table:

| The statement | Is |
| --- | --- |
| Names a table the schema does not have | `Unknown table` |
| Names a table a bucket generated | Refused by name, with its bucket |
| Names a field its table does not have | `Unknown field`, with the fields it has |
| Names a partition key, a sort key or a field with no role | `'x' is not a filter field of T: a SCAN reads its table whole and names filter fields only. To read by a key, SELECT` |
| Gives a filter field a value it cannot hold | `Type mismatch` |
| Has anything after its clauses | `Unexpected trailing input` |

Each error points at the text it is about, as a select's does.

**`SELECT` is unchanged.** It still requires a `WHERE` that constrains a partition key, so a query
that forgets its key is an error and never quietly a scan. `QuerySupport::parse` refuses a `SCAN`.

### A scan with its row type erased

`parse_scan` returns a `ShqlScan` (`shoal-proto/src/shared/queries/scan.rs`): the table's id and
name, its columns' headers, the scan's spec as archived bytes, its limit, and a function that reads
one page's body into each row's values as strings (`shql_rows::<Row>`, which validates every chunk
as a typed read does and formats each row through `TableRowFormat`).

`Shoal::scan_shql(scan)` and `Shoal::scan_text("SCAN ...")` return [F145](scan-driver.md)'s
`ScanBuilder`, whose rows are `Vec<String>`. To make that possible the driver no longer carries a
table's types: `ScanBuilder<'a, S, T>` and `Scan<'a, S, T>` are typed by what a row is handed out as,
and a scan is its table's id, its spec's bytes and a reader. A typed scan and a parsed one differ in
nothing after `start`.

A parsed scan asks for whole rows in the rows body. SHQL's `SCAN` names no projection.

### shoalctl

A query tab whose line begins with `SCAN` runs a scan instead of a query
(`shoalctl/src/components/tab.rs`, `run_scan`):

- The scan runs on a task of its own. It asks one page, sends it to the app, and waits.
- The tab draws every row handed out so far as one table, with a last line saying how many rows
  there are and whether the scan has ended.
- Scrolling down to the end of what is drawn asks for the next page.
- A page with no rows is not shown and not waited on: the next is asked at once.
- Running another query in the tab, or closing it, stops the scan. Its task drops the scan, which
  cancels the pages it has in flight.

A scan that is refused keeps the rows it handed out and shows the refusal under the query.

### The bench's driver

`ScanDriver::scan_once_client` (`shoal-loadgen/src/scans.rs`) reads a table whole through
`SCAN <table>` on its first member's client, and records each page in the second it was handed out:
the time the driver waited for it, its rows and its body's bytes. It is the way a standalone node is
scanned as a client scans it. `scan_once`, the admin walk, is unchanged and is what `shoaladm bench`
drives on a cluster, which answers no client's scan before
[M25](../future-work/scans/milestones.md).

### The example

`cargo run --example tmdb` reads its rows back a fifth way: a typed scan with a filter and a
projection, and a `SCAN` of each table counted a page at a time.

## Design choices

**A statement of its own.** `SELECT` without a key stays an error. A scan is the costliest read
there is, and should be something a caller wrote on purpose.

**Filter fields only.** A key named is a get: it has a shard to go to and an answer in one round.
Accepting a key in a `SCAN` would make two spellings of a get, one of them slow.

**The row type erased by a function pointer.** A caller that holds only a schema type, as shoalctl
and the bench do, cannot name `TableScan<Movie, Movie>`. The schema's derive can, once, for every
table, and hands back a plain `fn`. No trait object, no generic that the caller must fill.

**One driver.** The typed scan was refactored onto the erased core rather than given a sibling, so
streams, retries, tokens and cancels are one piece of code.

**The view asks, the task waits.** shoalctl's scan reads no further than its view has scrolled, so a
`SCAN` of a large table typed by mistake reads one page.

## Alternatives rejected

**A `SELECT` with no `WHERE` as a scan.** P24: no query becomes a scan by naming no key.

**Rows as JSON.** Each row would be serialized by one process and parsed by the same process to be
drawn. `TableRowFormat` already gives a row's values as the strings a table is drawn from.

**A projection clause on `SCAN`.** `SELECT <Projection> FROM` has one. It is a small addition, left
out because nothing here needs it and the typed scan has it.

**shoalctl reading the whole scan and then paging locally.** It would read a whole table to show a
screen of it.

**Switching `shoaladm bench` to the client's scan.** Its clusters grant no scans yet. It moves at
M25.

## Limitations

- **No projection, level or page bounds in the statement.** They are the builder's; a parsed scan
  can still be given `.level()` and `.page()` before `start`.
- **A parsed scan is answered in rows.** Partitions are a typed scan's.
- **shoalctl keeps every row it has shown in memory**, and redraws the whole table at each page.
- **shoalctl's paging was not driven by hand here.** It was compiled and its pieces are tested
  below; the machine it was built on has no terminal to drive a UI in. The scan it runs is the one
  `shql_scan_names_filters_and_refuses_a_key` runs.
- **`scan_once_client` records the time the driver waited for a page**, not a page's own round
  trip, since several streams' pages are in flight at once; and its end's `partitions` counts rows.
- **shoalctl's completion offers nothing for a `SCAN`.** It completes a `SELECT`'s tables and fields.
- **Keywords are matched as `SELECT`'s are**, and a table's name is case sensitive.

## Invariants to uphold

- **`SELECT` never scans**, and `parse` never accepts a `SCAN`.
- **A `SCAN` binds only filter fields.**
- **A parsed scan's reader validates every chunk before it formats a row**, as a typed read does.
- **A typed scan and a parsed one share the driver.** A fix to one is a fix to both.
- **shoalctl's scan task holds its scan, and nothing else does**: dropping the task's scan is what
  cancels its pages.

## Performance

Nothing on a query's path changed. `SCAN`'s own rate is the driver's, measured at [M24's lab exit](../future-work/scans/m24-exit.md) (2026-11-12).
